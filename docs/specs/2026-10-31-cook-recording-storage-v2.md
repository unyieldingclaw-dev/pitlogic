# Cook recording storage — revision 2

Status: proposed, not implementation approval. The user approved revising the rejected plan into separately reviewed usability and recording stages. This document supersedes the first storage amendment, retained as the [adversarial-review baseline](2026-10-31-cook-recording-storage.md). The equal-manual/RFX product direction remains approved. The project's localStorage-only rule is unchanged until this amendment is explicitly approved.

## Scope and evidence

Stage A improves navigation, essential manual-cook setup, device discovery, and connection clarity using existing storage. It does not migrate history, enable automatic cook recording, or expose a working RFX cook-source selector. Device readings must say they are not being saved into a cook. Both source paths have equal standing in the completed Stage B product; Stage A is an explicitly limited intermediate increment.

Stage B proposes native IndexedDB for authoritative cook metadata and readings; recipes, preferences, and connection configuration keep their localStorage keys. All data stays in this browser, offline-capable, with no server/account/dependency added. Moving manual cook metadata is proposed to obtain one transaction boundary for cook lifecycle and samples, not because manual histories were shown to exceed quota.

The [original capacity fixture](../qa/evidence/recording-storage-capacity.json) and [comparison](../qa/evidence/recording-storage-comparison.json) establish only the tested conditions: four probes/12 hours at 1 Hz exceeded localStorage with both tested representations; five-second histories fit in isolated desktop Chrome. Actual hardware cadence, IndexedDB capacity, and native mobile behavior remain unestablished. Preserving all accepted samples is the proposed policy. Decimation/retention changes would need separate approval.

## Database and identity contracts

Database `pitlogic-cooks`, version 1, with stores:

| Store | Key/index | Authoritative contents |
| --- | --- | --- |
| `cooks` | key `id` | Cook metadata, stable probe definitions, manual/RFX mode, active/complete status, recording authorization, binding intervals, latest committed summaries, live watermarks, recording interruptions |
| `readings` | key `[cookId, seriesId, sampleId]`; index `cookId` | Original minute time, captured `ts`, Fahrenheit `temp`, source manual/live/csv-import/legacy, optional device identity/receipt time, binding revision |
| `state` | key `key` | Active cook IDs/notices, dataset epoch, migration provenance, durable recovery/import state |
| `legacyConflicts` | key `revisionId` | Detected post-migration legacy snapshot, baseline identity, detection time; never silently merged with current data |

Series IDs are `food:<canonicalProbeId>` and `smoker`. Probe IDs are canonical strings: numeric 1 and string "1" identify the same candidate. Reject duplicate existing canonical IDs before any write. Missing legacy IDs receive deterministic `legacy:<originalIndex>` IDs, with a deterministic unused suffix if needed. Persist the mapping during migration. Never assign missing IDs solely from array indices that can collide with existing IDs. Preserve original IDs separately if their canonicalization affects exported representation. New probe/cook/sample identifiers use unique IDs, not millisecond-only IDs.

Live sample identity is `live:<deviceProbeId>:<capturedAt>` within cook/series. Equal-time conflicting live values keep the first accepted sample. Unique manual/CSV IDs preserve equal-time entries; legacy IDs use original series/row index. Materialized rows sort by captured time, then persisted insertion ordinal, preserving original equal-time order. Manual spot entries are explicitly manual and do not advance live watermarks.

Every asynchronous mutation carries its enqueue-time `datasetEpoch`. Every read/write transaction rechecks that epoch. Queries/hydration caches include epoch and cook ID; old responses cannot populate the new dataset. An epoch mismatch returns an explicit stale-dataset result without inserting rows or replaying them automatically.

## Migration, coexistence, and recovery (R4, R11)

1. Read the raw legacy `pitlogic-v5` without invoking a helper that rewrites it. Distinguish absent data from malformed/inaccessible data. Validate collections, IDs, timestamps and sample values; preserve all supported metadata and original sample values. Invalid data opens recovery, not a successful empty migration.
2. Before migration, offer a downloadable original snapshot and explain that older open app windows must be closed. Preserve the original localStorage value unchanged. In one IndexedDB transaction, write metadata, every legacy row, active state, initial epoch, baseline raw legacy snapshot, mapping, and completion marker. Abort leaves no completed migration; retry is idempotent.
3. Old uncooperative app versions cannot be made to respect a new IndexedDB lock. Do not promise an atomic cutover across old localStorage writers. New clients compare current raw legacy state with the baseline at open/focus and before/after mutations, and listen for storage changes. Include this check's cost in the large-legacy benchmark.
4. A detected change freezes new recording/mutations and preserves the detected raw snapshot in `legacyConflicts`. If IndexedDB cannot save that recovery copy, keep the raw legacy key untouched and offer its immediate download; do not overwrite either dataset. Durable conflict status is broadcast to cooperating new tabs. UI explains that an older window saved different data and offers export of both versions plus recovery preview. No automatic last-writer-wins merge or automatic return to the stale snapshot.
5. Explicit reconciliation requires closing older windows, comparing both recoverable versions, and a new import preview. Duplicate cook IDs with different contents are conflicts requiring a choice; unrelated IDs may merge after preview. A later old write triggers detection again. Pending/new committed data is retained separately; a detected conflict must not publish a new success label until the conflict is disclosed.
6. Reopen and compare the legacy snapshot even if a storage event was missed while closed. `versionchange` closes the new app's connection and prompts reload; `blocked` presents a close-other-windows recovery action. New tabs use BroadcastChannel for prompt invalidation, but correctness comes from transaction checks/provenance, not message delivery.
7. Deliberate rollback still sees only the preserved legacy snapshot. Export a current self-contained backup before rollback; do not describe that older snapshot as up-to-date. No automatic deletion of legacy data/backups occurs.

Tests must exercise old-app writes after migration, missed events/reopen, concurrent new tabs, blocked/versionchange, malformed data, mixed missing/existing IDs, aborted migration, and recovery-copy failure. PWA upgrade testing must enable real cache behavior on an isolated test origin; localhost previews bypass the current service worker and are insufficient for this gate. Any needed deployment-cache change is separately reviewed before editing it.

## Replacement/import fence and mixed-storage import (R5, R7)

All new writers acquire the current epoch at enqueue. Restoring a dataset first pauses local intake and drains or explicitly cancels queued work. A single replacement transaction increments the persisted epoch, replaces cooks/readings/state, and journals any pending recipe work. Another tab's append serialized before replacement is replaced; one serialized afterward with the old epoch is rejected. Retry batches retain their original epoch and cannot be relabeled to the new dataset. New clients observe the new epoch, clear obsolete read caches, and pause imported RFX sessions until the user verifies and resumes them. Restoring the same cook/channel IDs never automatically reauthorizes an old job.

Settings awaits cook import before attempting recipe changes, clearing preview, or closing. A cook-transaction rejection changes no recipes and retains the preview. Recipes live in localStorage, so whole-backup import is not one atomic transaction across both engines. On cook success/recipe failure, retain a durable journal of the recipe target and original recipe revision, show "Cooks imported; recipes not imported", keep recovery visible, and offer idempotent Retry recipes or export of current results. Both the FIRST recipe application and every retry verify import ID, resulting dataset epoch and expected recipe revision; no stale operation can complete against a newer dataset. No generic Import complete label appears until both parts finish. No silent compensating overwrite or automatic rollback of newer data.

Cross-tab coordinator: the cook-replacement transaction creates `state.pendingImport = { importId, resultingEpoch, originalRecipeRaw, targetRecipeRaw, phase }`. While this durable operation is pending, all cooperating clients reject a second import and unrelated recipe mutation with a visible Finish/recover current import action. Do not expire or steal the pending operation automatically. Reload recovery resumes the SAME import ID and epoch. Normal recipe add/update/delete/CSV/replace operations use this same coordinator, not an unguarded localStorage path, and obtain a durable pending recipe operation before writing.

Recipe application obtains an IndexedDB readwrite transaction on the shared state store, validates the pending operation/current epoch/expected raw recipe revision, and performs its synchronous localStorage write inside that request callback without yielding. Other cooperating writers serialize on this state store. Publish React success only after transaction completion. This does not make the two engines atomic: if localStorage writes successfully and the IndexedDB transaction then aborts, the PREVIOUSLY committed pending journal remains. Recovery recognizes raw recipes equal to the operation target, marks that operation complete idempotently, and never reapplies a stale snapshot. If raw recipes equal neither baseline nor target, show conflict preview instead. Store operation revisions separately so the recipe array format need not change. Do not call the current recipe hook, which swallows storage errors, as the persistence authority.

Old uncooperative recipe writers cannot be locked out. The initial recipe snapshot and target are recoverable in the journal; monitor recipe storage events (including their revision values), reopen/focus and first/retry apply for divergence. Tell the user to close older windows before restore; detect/disclose conflicts rather than promising exclusion. Recipe read/list/export remains available when the coordinator fails; any blocked write reports an error instead of publishing Saved.

Required tests: delayed FIRST recipe apply while another tab attempts import/edit, pending operation across reload, real localStorage.setItem rejection through the recipe hook/adapter, localStorage success followed by IndexedDB abort, old-writer divergence, and stale import completion after epoch change. None may claim complete or overwrite another operation silently.

Validate cook/probe/source/binding/readings schemas at backup boundaries, not merely top-level arrays. Existing version-1 backups remain readable. Export includes all committed readings/source and binding history, not database references; it flushes or reports pending/failed samples explicitly. Export success does not imply a prior failed sample was saved.

## Probe association and recording boundaries (R6)

Each binding has `{ revision, deviceProbeId, seriesId, validFrom, validUntil }` using the capture-time domain accepted by normalization; `validUntil` is exclusive and null while current. Assignment/replacement commits its new boundary before accepting new-channel samples. Accept a sample only when its capture time lies in that binding interval, its enqueue-time binding revision matches, its dataset epoch matches, and the cook is active. Queue entries never have their revision rebound during a retry. If source/client clock discrepancy prevents proving eligibility, show Waiting for a reading captured after selection; do not relax the boundary silently. Hardware clock behavior is a release test.

The active-cook screen has **Change food probe** (and Change smoker probe when bound), displays old/new identities, validates exclusive food ownership, and asks for explicit confirmation. Before confirmation commits, pause intake for this cook and flush its eligible old-revision batch. If that fails, retain the binding and expose recovery; do not silently discard pending readings. The transition transaction closes the prior interval, preserves prior samples, adds a recording-gap marker, and waits for an eligible replacement reading. After it commits, delayed old-revision jobs are explicitly rejected and never rebound; a pending-reading recovery download remains available. Other cooks and device hardware configuration are untouched. An old channel or its retained reading cannot resume ownership. Ambient sharing requires explicit cook selection and retains separate per-cook intervals. Selecting the same food channel for two active cooks is rejected transactionally.

Tests include the review's 10:00 cook/10:20 assignment/10:10 retained sample scenario, reload/retry, two different replacement channels, old-channel late packets, ownership conflicts, and a replacement performed during pending writes.

## Event bridge, batching, and truthful status (R8)

The store exposes every accepted reading through the existing permitted `useTelemetryStore` boundary; React snapshot coalescing is never the recording input. Only normalized source `live` enters RFX recording. Validate finite temperature, capture bounds, interval/revision, active status, recording authorization and watermark inside the database transaction. A restored RFX cook has recording authorization false until explicit verify/resume; an incoming event with a newly observed epoch does not enable it. Metadata/battery changes, CSV replay, and synthetic normalized events do not masquerade as live samples.

Batch at most every 250 ms and retain at most 1,000 uncommitted samples. A write failure/queue bound pauses automatic recording, retains the bounded batch for retry, and exposes subsequent missing data as a gap. Stop treating new received values as committed. Stable IDs, epoch and binding revision make retry idempotent. End cook and export await flush. When flush fails, keep the cook open with a visible recovery route; offer download of pending readings and an explicit finish-with-gap action instead of silently discarding them. A successful end transaction makes the session immutable to later telemetry.

Per-channel status includes `{ cookId, seriesId, datasetEpoch, bindingRevision, deviceProbeId, latestReceivedAt, latestCapturedAt, lastCommittedSampleId, lastCommittedAt, pendingCount, connectionStatus, persistenceError }`. UI derives receiving/pending/committed/stale/missing/paused separately for each selected cook/channel. A shared ambient value or another cook's success cannot turn a missing food channel green. Overall state may be Partially recording; show which channel needs action. Manual mode displays entry time/source and saving/failed status without a Live label.

No recording or browser notification guarantee is made for locked/suspended/closed apps. On resume/reload, show a detected interval gap and actual reconnect state; no invented backfill. Foreground-only behavior remains a product limitation requiring real-device acceptance, not a problem solved by IndexedDB.

## Materialized history and current advice (R1, R2, R3, R9)

Repository list queries return a distinct summary type, not Cook objects with fake empty `readings`. `useCookHistory({ datasetEpoch, cookIds })` provides `{ status: loading/ready/error, cooks, error, retry }`. It resolves only after all requested IDs have full committed histories and ignores obsolete epoch/selection results. Active views load relevant active histories; detail loads selected and compared histories; Stats/Compare explicitly request all completed IDs they consume. Active StallCoach independently requests completed histories matching the active cut, showing loading/error only for its historical-advice section without blocking current temperatures or guessing an empty prediction. Changing active cook/cut or dataset invalidates that request. Until ready, all historical consumers show loading/error, never zero-history analytics. Source labels survive every projection/export.

Full-history peak/range calculations use bounded iteration, never an unbounded spread. Inspect History, Dashboard summaries, Detail, CompareChart, ShareCard and Analytics consumers. Charts build rows in one pass. Display a bounded min/max envelope preserving extrema, first/last and gap boundaries; preserve raw samples unchanged. Never connect chart lines across explicit collection gaps.

Analytics use elapsed-time windows rather than N-adjacent-sample windows. Proposed fixed calculation policy: current rate uses the trailing 30-minute curve, requires at least 5 minutes of covered data, and fits a uniformly spaced one-minute derived curve with boundary interpolation only inside covered intervals. Confirmed stall requires a covered trailing 18 minutes, temperature 140–185°F, range <8°F; approaching stall requires covered 12 minutes and range <5°F. Use actual raw extrema for stall ranges. Never interpolate across recorded interruptions, device gaps >30 seconds, or manual gaps >15 minutes. Missing coverage yields Insufficient recent data, not Normal. Historical stall uses the same elapsed-time/coverage policy; raw rows remain stored at original cadence.

Current RFX advice/alerts require a fresh supporting captured sample (30 seconds, aligned with existing stale policy), committed to this cook and not after a gap. Manual estimates identify the entry time and cease current-action claims after 15 minutes. LiveIntelligence, StallCoach (including its displayed stall duration), App stall/wrap/carryover, ETA/Done and notification hooks all consume this eligibility/elapsed-time contract; StallCoach must not retain its separate slice(-4) duration. Static cook guides remain available; their content is not current sensor advice. Compare equivalent flat/rising/stall/noisy/dropout curves at sparse, irregular and 1-Hz cadence; exact linear fixtures require rate agreement within 0.1°F/hour and ETA within 1 minute. Nonlinear/noisy fixture tolerances must be recorded with expected behavior before coding; no blanket numerical equivalence claim across information-losing sample cadences.

## Verification and resource budgets (R10)

Use a virtual capture clock and the real normalization/recording path, pacing accelerated batches through actual database completion. Do not flood 172,800 events without yielding and then call queue overflow an ingestion-capacity result. Verify overload separately by intentionally exceeding the bound and expecting an explicit pause/gap.

Reference desktop Chrome gates, measured on the same machine/build with five warm-up runs and at least twenty measured runs per checkpoint:

- 172,800 exact samples across a 12-hour/four-probe/1-Hz cook; zero silent loss, wrong sources, or cross-cook assignments.
- Fixed 250-sample transaction batches at early/middle/final database sizes: p95 commit <=250 ms and final <=2× early p95. Include the cost of legacy-provenance checks.
- Navigation click to matching visible page p95 <=250 ms during ingestion; first completed detail or Stats ready <=2 seconds for the fixture. Measure the rendered result, not only a pure chart function.
- Per-series chart envelope <=1,200 display points including first/last/gap markers; if gap count alone exceeds the budget, disclose limited display while keeping all raw history and gap intervals accessible. Never silently erase gaps to pass a point cap.
- Export and reimport four archived 172,800-sample cooks (691,200 total) with exact values/counts, stable source/order, output bytes, and forced-failure recovery. Use a dedicated worker for JSON conversion/validation to keep main-thread responsiveness; no more than 100 ms p95 measured main-thread scheduling delay in the reference run. Completion <=15 seconds per operation. Main and dedicated-worker JS heaps together <=512 MiB in the controlled reference fixture, measured through available browser instrumentation. If memory instrumentation is unavailable, that gate is unverified, not passed. Main-thread heartbeat/interaction measurements continue during worker work.

These are proposed acceptance budgets for this implementation, not claims about all hardware. Record absolute distributions, fixture sizes, browser version, build and machine. Investigate failures rather than loosening thresholds after seeing results. Real phone/device, PWA upgrade/cache, locking/background, storage eviction/quota and actual unattended-duration gates remain necessary before release. Browser database storage is not a backup against clearing site data; the UI must keep export discoverable.

## Approval boundary

It does not demonstrate that any proposed repository, recorder, migration, or background behavior works: none exists yet. Stage A can be approved separately without approving this database migration. Stage B and the localStorage-rule exception require separate approval after re-review.
